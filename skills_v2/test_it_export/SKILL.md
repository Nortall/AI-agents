# Экспорт в Test IT

## Назначение

Скилл преобразует уже готовую тестовую документацию в формат, совместимый с импортом Test IT.

Допускается только изменение структуры представления данных. Скилл **не** анализирует требования, **не** проектирует проверки, **не** определяет приоритет, **не** добавляет и не удаляет проверки, **не** исправляет ошибки генерации.

Если исходные тест-кейсы содержат дефекты — экспортируй как есть и сообщи о них отдельно.

## Структура XLSX

15 колонок строго в указанном порядке. Изменение порядка запрещено.

| № | Колонка | № | Колонка |
|---|---|---|---|
| 1 | Название | 9 | Действие постусловия |
| 2 | Описание | 10 | Ожидаемый результат постусловия |
| 3 | Статус | 11 | Продолжительность |
| 4 | Приоритет | 12 | Секция |
| 5 | Действие | 13 | Тестовые данные |
| 6 | Ожидаемый результат | 14 | Ревью |
| 7 | Действие предусловия | 15 | Вид |
| 8 | Ожидаемый результат предусловия | | |

## Header-строка

Одна на каждый тест-кейс. Заполняются только поля: Название, Описание, Статус, Приоритет, Продолжительность, Секция, Ревью, Вид. Остальные остаются пустыми.

**Название** — краткое и однозначное название тест-кейса.

**Описание** — единый формат:

```
Источник: <путь требования>
Требование: <описание требования>
```

Пример:
```
Источник: Solo Exhibition > Блоки для редактора > Заглавный блок
Требование: Заглавный блок / Название
```

Расширения файлов не указываются — не писать `.md`.

**Статус** — всегда `Готов`.

**Продолжительность** — ориентировочное время ручного прохождения в формате `0h 10m 0s`.

**Секция** — полный путь существующей папки Test IT. Не изменять структуру секций и не создавать новые без явного указания.

**Ревью** — всегда `Не пройдено`.

**Вид** — `Позитивный` или `Негативный`. Значение берётся из входных данных: его назначает `test_case_generation` или `checklist_generation`.

Если вид на входе не указан — не определяй его самостоятельно, это решение о содержании. Запроси недостающие значения.

## Маппинг приоритетов

Генерация использует трёхуровневую шкалу, Test IT — пятиуровневую. Преобразование однозначное:

| Приоритет на входе | Значение в Test IT |
|---|---|
| Высокий | `Высокий` |
| Средний | `Средний` |
| Низкий | `Низкий` |

Значения `Самый высокий` и `Самый низкий` в Test IT существуют, но по умолчанию **не используются**. Присваивать их только по явному указанию пользователя.

Если на входе встретилось значение вне трёхуровневой шкалы — не угадывай, запроси уточнение.

## Child-строки

Каждый шаг тест-кейса оформляется отдельной строкой.

| Тип строки | Заполняемые колонки |
|---|---|
| Предусловие | Действие предусловия (7). Ожидаемый результат предусловия (8) обычно пуст |
| Основной шаг | Действие (5) + Ожидаемый результат (6) — оба обязательны |
| Постусловие | Действие постусловия (9) + Ожидаемый результат постусловия (10) |

Каждое действие имеет собственный ожидаемый результат. Объединять несколько действий в одной строке запрещено.

Колонка «Тестовые данные» не заполняется, если это не требуется явно.

## Экспорт чек-листа

**Ограничение импорта, подтверждено на практике: XLSX-импорт Test IT создаёт только тест-кейсы.**

В самой Test IT чек-лист существует как отдельный тип рабочего элемента, и поля ожидаемого результата у его шагов нет. Но через импорт этот тип не создаётся — что бы ни было в файле, на выходе получаются тест-кейсы.

Следствия:

- Выгруженный чек-лист приходит в Test IT тест-кейсом, шагами которого стали пункты, а ожидаемые результаты пустые. Это осознанный компромисс, а не перенос чек-листа.
- Если набор изначально предназначен для Test IT — генерируй тест-кейсы, а не чек-лист. См. `test_case_generation`, раздел «Выбор формата».
- Чек-лист, который должен остаться чек-листом, создаётся в интерфейсе Test IT вручную.

Ниже — раскладка файла для случая, когда выгрузка чек-листа всё же нужна. Один чек-лист даёт один рабочий элемент, его пункты становятся шагами.

| Строка | Что заполняется |
|---|---|
| Header — одна на весь чек-лист | Название чек-листа, Статус, Приоритет, Продолжительность, Секция, Ревью, Вид |
| Child — одна на каждый пункт | Только «Действие» (5). «Ожидаемый результат» (6) остаётся пустым |

Шаг чек-листа может содержать многострочный текст с вложенными буллитами — перечисление внутри одного пункта допустимо.

**Типичная ошибка:** оформить каждый пункт отдельной Header-строкой. При импорте это создаёт по рабочему элементу на пункт, и все они приходят с пустым телом — без шагов и предусловий.

### Приоритет и вид при разбиении

Приоритет и вид — атрибуты рабочего элемента целиком, а не отдельного пункта. Если пункты чек-листа имеют разные приоритеты, создавай **отдельный чек-лист на каждую группу приоритета**, иначе приоритеты пунктов будут потеряны.

Название группы должно оставаться различимым: `Футер сайта — высокий приоритет`.

То же правило действует, если в чек-листе смешаны позитивные и негативные пункты.

Поле «Описание» заполняется только если источник требования известен. Недостающие шаги **не достраиваются** — это изменило бы содержание.

### Проверено импортом

| Что выгружается | Результат в Test IT |
|---|---|
| Тест-кейсы | Импортируются корректно: Header-строка даёт тест-кейс, дочерние строки — предусловия и шаги с ожидаемыми результатами |
| Чек-лист | Создаются тест-кейсы, а не чек-листы. Тип сущности через файл импорта не задаётся |

Формат из 15 колонок для тест-кейсов подтверждён на реальном импорте. Менять его порядок и состав без необходимости не нужно.

## Проверка перед выдачей результата

- порядок колонок соответствует шаблону;
- каждая Header-строка содержит все обязательные поля;
- каждое действие имеет ожидаемый результат;
- каждое постусловие имеет ожидаемый результат;
- приоритеты преобразованы по таблице маппинга;
- отсутствуют лишние секции;
- отсутствуют дубли тест-кейсов внутри одной секции;
- текст тест-кейсов не изменён относительно исходного.

## Генерация файла

Используй `templates/test_it_generator.py` как основу — подставь свои данные в `CASES` и запусти. Путь к выходному файлу передаётся первым аргументом.

Скрипт принимает обе формы данных в одном списке:

| Что выгружается | Ключи записи |
|---|---|
| Тест-кейс | `name`, `desc`, `priority`, `duration`, `section`, `review`, `type` + `preconditions`, `steps`, `postconditions` |
| Пункт чек-листа | те же ключи без `preconditions`, `steps`, `postconditions`; `desc` необязателен |

Пункт чек-листа даёт одну Header-строку без дочерних. Разделительная пустая строка ставится только после записей с дочерними строками.

```bash
python3 test_it_generator.py /путь/к/output.xlsx
```

## Питфолы openpyxl

Эти ошибки повторяются регулярно — проверь до запуска.

**1. Имя переменной совпадает с параметром функции**

Не называй список тест-кейсов `tc`, если параметр функции-обработчика тоже `tc`. Python не выдаст ошибку, но функция прочитает список вместо словаря → `KeyError`.

```python
# Плохо
tc = [{"name": "TC-001", "duration": "0h 10m 0s"}]
def write_header(tc):        # перекрывает список
    print(tc["duration"])    # KeyError

# Хорошо
cases = [{"name": "TC-001", "duration": "0h 10m 0s"}]
def write_header(d):
    print(d["duration"])
```

**2. Расхождение ключей данных и кода**

Выведи `print(list(cases[0].keys()))` перед циклом и сверь с тем, что читают функции. Частая ошибка: в данных `"duration"` и `"section"`, а код читает `"dur"` и `"sec"`.

**3. Фигурные скобки в русском тексте внутри f-строки**

F-строки интерпретируют `{любое_слово}` как подстановку переменной. Русский текст в фигурных скобках ломает генерацию с `NameError`.

```python
# Плохо
f"Требование: +{количество} по выбору"    # NameError

# Хорошо — экранировать удвоением
f"Требование: +{{количество}} по выбору"  # → «+количество по выбору»
```

Если в строке нет подстановок — не делай её f-строкой.

Перед запуском прогони синтаксическую проверку, она ловит такие ошибки до `wb.save()`:

```bash
python3 -c "compile(open('test_it_generator.py').read(), 'test_it_generator.py', 'exec')"
```

**4. Задержка сохранения файла**

После `wb.save()` подожди 1–2 секунды перед проверкой наличия файла. На macOS файл может быть создан, но ещё не отображаться в файловой системе.

## Рекомендуемый порядок работы

1. Собери данные с полным набором ключей: `name`, `desc`, `priority`, `duration`, `section`, `review`, `type`, `preconditions`, `steps`.
2. Дай параметрам функций имена, отличные от имён переменных с данными.
3. Проверь ключи через `print(list(cases[0].keys()))`.
4. Прогони синтаксическую проверку.
5. Запусти генерацию и убедись, что файл создан и его размер больше нуля.
