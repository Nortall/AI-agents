# Самопроверка перед выводом

Выполняется **внутренне**, до вывода результата. Результаты самопроверки пользователю не показываются.

Порядок проверок важен: сначала трассируемость (что не должно существовать), затем фрагментация (как сгруппировано), затем качество формулировок.

---

## 1. Трассируемость

### Тест → требование

Для каждого теста определи требование-источник.

Допустимые источники:

- основной сценарий
- альтернативный сценарий
- критерий приёмки
- явно сформулированное бизнес-правило
- нефункциональное требование
- логическая зависимость, выявленная на этапе анализа вариативности

Тест без источника происхождения удаляется.

### Требование → тест

Пройди по каждому требованию и критерию приёмки и убедись, что его покрывает хотя бы один тест.

Непокрытое требование → добавь тест.

### Допустимость тестов из анализа вариативности

Тест, не описанный в требованиях напрямую, допустим, если одновременно:

1. Логически следует из свойств объекта (сущность может быть создана → значит, может быть удалена).
2. Проверяет реакцию зависимых объектов на изменение родительского.
3. Не утверждает конкретное поведение системы.

Пример допустимого: требование «пользователь может создать период с карточками» → тест на реакцию карточек при удалении периода. Источник: логическая зависимость «период → карточки».

Недопустимо: вводить сущности, статусы и правила, которых нет в требованиях.

---

## 2. Обнаружение галлюцинаций

Признаки:

- тест не связан ни с одним требованием
- тест использует несуществующие сущности, статусы или коды ошибок
- тест опирается на неописанное бизнес-правило
- тест утверждает конкретное поведение, которое в требованиях не зафиксировано

**Пример:**

Требование: «Пользователь регистрируется.»
Сгенерированный тест: «Проверка статуса `pending_activation`.»

Статус `pending_activation` в требованиях отсутствует → тест удаляется.

---

## 3. Контроль фрагментации

Посчитай соотношение: количество тестов к количеству ключевых требований (определение — в `SKILL.md`, раздел «Определение объёма работы»).

Если тестов более чем втрое больше — набор фрагментирован, вернись к группировке по бизнес-идеям.

Ситуация «одно требование → много тестов» недопустима, если все эти тесты проверяют одно и то же бизнес-правило. Если требование содержит несколько разных правил — несколько тестов правомерны.

**Нарушение:**
```
A2 Невалидный email → TC-003 отсутствует «@»
                    → TC-004 отсутствует домен
                    → TC-005 отсутствует локальная часть
```

**Решение:** объединить проверки валидации одного поля в один тест-кейс.

---

## 4. Таблица антипаттернов

| Антипаттерн | Признак | Решение |
|---|---|---|
| Полевой тест | «Поле X отображено / скрыто» как отдельный тест | Объединить с проверкой блока целиком |
| Дублирующий счастливый путь | Один и тот же сценарий для разных ролей | Один тест с перечислением ролей, если поведение совпадает |
| Контекстный разброс | Отдельный тест на каждый контекст одного элемента | Объединить, если поведение одинаковое |
| Zero-тест | Отдельный тест на значение 0 или NULL для каждого поля | Объединить граничные zero/null-случаи |
| Button-only | «Кнопка отображена» без последующего действия | Объединить с навигацией или основным сценарием |
| Тривиальный тест | Проверка, не несущая бизнес-риска | Удалить, кроме критичных точек входа |

---

## 5. Атомарность

Каждый тест проверяет **одну** бизнес-идею.

Признак нарушения — условные конструкции в теле теста: «если … то …», «иначе …», «в случае …», «при наличии …».

**Плохо — две ветви в одном тесте:**
```
Если пользователь администратор — отображена кнопка удаления.
Если пользователь менеджер — отображена кнопка редактирования.
```

**Хорошо:**
```
TC-001 — Отображение кнопки удаления для администратора
TC-002 — Отображение кнопки редактирования для менеджера
```

Тест неатомарен, если содержит несколько альтернативных путей выполнения. Такие тесты разделяются.

Атомарность не противоречит группировке: объединять можно проверки **одной** бизнес-идеи, разделять нужно **разные** ветви логики.

---

## 6. Воспроизводимость

Тест должен быть выполним специалистом, не знакомым с проектом.

Недопустимы абстрактные формулировки без расшифровки: «корректные данные», «вызвать ошибку», «инициировать сбой», «выполнить частичный отказ».

Если тест требует моделирования специальных условий, способ их воспроизведения описывается явно.

---

## 7. Тестовые данные

Не использовать неопределённые формулировки. Указывать класс значения, а не абстракцию.

| Плохо | Хорошо |
|---|---|
| валидный email | email в формате `user@example.com` |
| слабый пароль | пароль длиной 5 символов |
| корректные данные | обязательные поля заполнены допустимыми значениями |

Привязывать тест к классу эквивалентности, а не к единственному фиксированному набору данных. Конкретные значения выбираются позже, на этапе подготовки к выполнению.

---

## 8. Соответствие шаблону

- количество пунктов «Ожидаемый результат» строго равно количеству шагов;
- каждый шаг содержит одно действие;
- ожидаемый результат сформулирован в прошедшем времени;
- предусловия не содержат действий пользователя;
- у каждого теста назначен приоритет;
- у каждого теста назначен вид — `Позитивный` или `Негативный`;
- настройка, не являющаяся предметом проверки, вынесена в предусловия, а не в шаги.

Полные правила — в `references/template.md`.
