# Техники тест-дизайна

## Выбор техники

Техника выбирается под форму требования, а не применяется списком подряд.

| Что в требовании | Техника |
|---|---|
| Поле ввода с ограничениями (формат, длина, диапазон) | Классы эквивалентности + граничные значения |
| Несколько условий совместно определяют результат | Таблица решений |
| Объект с жизненным циклом или статусами | Переходы состояний |
| Несколько независимых параметров (фильтры, настройки, флаги) | Попарное тестирование |
| Пользовательский сценарий | Позитивный путь + негативные пути |
| Обработка ошибок и сбоев | Догадки об ошибках |

Одно требование может потребовать нескольких техник. Если две техники дают одну и ту же проверку — тест создаётся один раз.

---

## Позитивное и негативное тестирование

**Позитивное** — успешное выполнение основного сценария при корректных данных.

**Негативное** — ошибочные и альтернативные сценарии: некорректные данные, отсутствие прав, недоступность зависимой системы, нарушение бизнес-правила.

На каждый основной сценарий обязателен минимум один позитивный тест. Негативные покрываются по классам ошибок, а не по каждому отдельному некорректному значению.

---

## Классы эквивалентности

Входные данные разбиваются на группы, внутри которых система ведёт себя одинаково. Из каждого класса проверяется **один** представитель — остальные значения класса избыточны.

**Email:**
- валидный: `user@example.com`
- без символа «@»: `userexample.com`
- без доменной части: `user@`
- без локальной части: `@example.com`

**Пароль:**
- соответствует всем требованиям
- короче минимальной длины
- без обязательного класса символов

Классы формируются как по допустимым, так и по недопустимым значениям. Проверка двух значений из одного класса — дублирование.

---

## Анализ граничных значений

Границы — наиболее дефектоопасные точки. Для каждой границы проверяются три значения: на границе, непосредственно под ней, непосредственно над ней.

**Минимальная длина пароля 8 символов:**
- 7 символов — ниже границы
- 8 символов — на границе
- 9 символов — выше границы

Если диапазон ограничен с двух сторон — проверяются обе границы.

**Количество элементов в списке, максимум 100:**
- 0, 1, 99, 100, 101

Границы применяются к длине строк, числовым диапазонам, количеству объектов, датам и размерам файлов.

---

## Таблица решений

Применяется, когда результат определяется комбинацией нескольких условий. Позволяет не пропустить комбинацию и не создать избыточные тесты.

**Алгоритм:**

1. Выпиши условия, влияющие на результат.
2. Выпиши возможные действия системы.
3. Построй таблицу комбинаций условий.
4. Исключи логически невозможные комбинации.
5. Каждый оставшийся столбец = один тест.

**Пример — доступ к разделу:**

| Условие | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| Пользователь авторизован | Да | Да | Да | Нет |
| Роль имеет право доступа | Да | Да | Нет | — |
| Подписка активна | Да | Нет | — | — |
| **Результат** | Доступ открыт | Предложение продлить | Ошибка доступа | Переход на авторизацию |

Прочерк означает, что значение условия не влияет на результат — это и позволяет сократить набор.

Если условий много и они независимы, таблица решений избыточна — используй попарное тестирование.

---

## Переходы состояний

Применяется к объектам с жизненным циклом.

**Алгоритм:**

1. Выпиши состояния объекта из требований.
2. Выпиши разрешённые переходы.
3. На каждый разрешённый переход — один тест.
4. На ключевые запрещённые переходы — негативные тесты.

**Пример — заказ:**

Состояния: создан → оплачен → отправлен → доставлен; отменён.

Разрешённые переходы (позитивные тесты):
- создан → оплачен
- оплачен → отправлен
- отправлен → доставлен
- создан → отменён
- оплачен → отменён

Запрещённые переходы (негативные тесты):
- доставлен → отменён
- создан → отправлен (в обход оплаты)

Состояния и переходы берутся только из требований. Если жизненный цикл не описан — техника не применяется.

---

## Попарное тестирование

Применяется, когда несколько независимых параметров имеют по несколько значений и полный перебор избыточен.

Большинство дефектов проявляется при взаимодействии не более двух параметров, поэтому достаточно покрыть все пары значений, а не все комбинации.

**Пример — фильтр каталога:**

- Категория: 3 значения
- Сортировка: 3 значения
- Способ отображения: 2 значения

Полный перебор — 18 комбинаций. Попарное покрытие — 9, при этом каждая пара значений встречается минимум один раз.

Не применять, когда конкретная комбинация критична для бизнеса — такие комбинации проверяются явно, через таблицу решений.

---

## Догадки об ошибках

Проверки на основании типичных дефектов, не описанных в требованиях явно:

- пустые значения и отсутствующие обязательные поля
- дубликаты данных при ограничении уникальности
- спецсимволы и пробелы по краям значения
- сверхдлинные значения
- некорректный формат данных
- повторная отправка формы / двойной клик
- параллельное изменение одной записи
- недоступность внешнего сервиса, таймаут, ошибка 5xx
- потеря соединения в середине операции

Техника применяется последней — после неё проверь, не дублирует ли результат уже созданные тесты.

---

## Контроль избыточности

После применения техник:

- проверки, полученные разными техниками, но проверяющие одну бизнес-логику, объединяются;
- из каждого класса эквивалентности остаётся один представитель;
- техника, не давшая новых проверок, не добавляет тестов «для полноты».
