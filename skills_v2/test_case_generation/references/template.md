# Шаблон тест-кейса и формат вывода

Структура обязательна к соблюдению и совместима с импортом в Test IT.

## Атрибуты

Каждый тест-кейс содержит:

- Наименование
- Приоритет
- Вид
- Предусловия
- Шаги
- Ожидаемый результат для каждого шага
- Постусловия (если требуются)

## Формат вывода

```
TC-001 – Название

Приоритет: Высокий
Вид: Позитивный

Предусловия:
1. ...
2. ...

Шаги:
1. ...
2. ...
3. ...

Ожидаемый результат:
1. ...
   * детализация
   * детализация
2. ...
3. ...
```

## Наименование

Название должно:

- кратко описывать проверяемую функциональность;
- содержать одну бизнес-идею;
- быть понятным без чтения шагов.

| Плохо | Хорошо |
|---|---|
| Проверка регистрации | Регистрация пользователя с корректными данными |

## Вид

Обязательный атрибут. Допустимы ровно два значения: `Позитивный` и `Негативный`.

| Вид | Что проверяет |
|---|---|
| **Позитивный** | Штатное поведение системы при корректных условиях — включая корректную реакцию на отсутствие данных, пустые списки и скрытые блоки, если это предусмотренное поведение |
| **Негативный** | Реакцию на нарушение правила: некорректный ввод, превышение ограничения, отсутствие прав, недоступность зависимой системы |

Разграничение определяется не результатом, а причиной. Отсутствие данных при корректной конфигурации — позитивный тест: система ведёт себя как задумано.

| Тест | Вид | Почему |
|---|---|---|
| Блок не отображается, так как значения не заполнены | Позитивный | Предусмотренное поведение, правило не нарушено |
| Отображено сообщение об ошибке при пустом обязательном поле | Негативный | Нарушено правило обязательности |
| Промокод не применён, так как сумма заказа ниже минимальной | Негативный | Нарушено бизнес-правило |
| Список пуст, так как ни одна запись не создана | Позитивный | Штатное состояние системы |

Если тест содержит и корректный, и ошибочный путь — он неатомарен и подлежит разделению.

## Предусловия

Описывают состояние системы до начала выполнения теста.

- каждое предусловие оформляется отдельным пунктом;
- предусловия должны быть проверяемыми;
- предусловия не содержат действий пользователя.

**Хорошо:**
```
1. Пользователь авторизован.
2. В системе существует период обучения.
```

**Плохо:**
```
Пользователь авторизуется.
```

## Шаги

Один шаг — одно действие пользователя.

- действия выполняются последовательно;
- шаг должен быть воспроизводимым;
- не объединять несколько действий в одном шаге.

**Хорошо:**
```
1. Открыть страницу регистрации.
2. Заполнить поле Email.
3. Нажать кнопку «Создать».
```

**Плохо:**
```
Открыть страницу, заполнить форму и нажать кнопку.
```

## Смена актора внутри теста

Правило «шаг — одно действие пользователя» не означает, что все шаги выполняет один актор. Проверка поведения клиентской части часто требует настройки в административной панели.

Приоритет: сначала попытайся вынести настройку в **предусловия** — тест становится короче и проверяет одну идею.

```
Предусловия:
1. В административной панели у категории деактивирован чекбокс «Отображать на сайте».

Шаги:
1. Открыть страницу каталога.
```

Включай действие другого актора **в шаги** только тогда, когда проверяется сам факт изменения — то есть переход системы из одного состояния в другое.

```
Шаги:
1. Деактивировать чекбокс «Отображать на сайте» у категории и сохранить изменения.
2. Обновить страницу каталога.
```

Когда акторов несколько, каждый шаг начинается с указания исполнителя, если он сменился относительно предыдущего шага. Смена актора не отменяет правило 1:1 и не даёт объединять действия в одном шаге.

## Тесты на уровне API

Шаблон применяется к API-тестам без изменений. Меняется только характер действия: шаг описывает запрос, а не действие в интерфейсе.

```
Предусловия:
1. Получен токен авторизации пользователя с ролью «Менеджер».
2. В системе существует заказ в статусе «Создан».

Шаги:
1. Выполнить POST /orders/{id}/cancel с валидным токеном.
2. Выполнить GET /orders/{id}.

Ожидаемый результат:
1. Возвращён код 200.
   * В теле ответа статус заказа — «Отменён».
2. Возвращён код 200.
   * Статус заказа в ответе — «Отменён».
```

Эндпоинты, коды ответов и поля указываются только те, что описаны в требованиях. Если контракт API в требованиях отсутствует — тест формулируется на уровне поведения, а метод и путь выносятся в вопросы.

## Ожидаемый результат — правило 1:1

**Количество пунктов верхнего уровня в секции «Ожидаемый результат» строго равно количеству шагов в секции «Шаги».**

Это единственный источник истины по правилу 1:1.

- Шаг 1 → Ожидаемый результат 1. Шаг 2 → Ожидаемый результат 2.
- Нет шагов без ожидаемого результата.
- Нет ожидаемых результатов без соответствующего шага.
- Никогда не создавать больше пунктов ожидаемого результата, чем шагов.
- Если шаг проверяет несколько аспектов — они оформляются вложенными буллитами под своим номером.

**Пример:**

Шаги:
```
1. Кликнуть на поисковую строку.
2. Ввести текст.
3. Нажать Enter.
```

Ожидаемый результат:
```
1. Отображён выпадающий список подсказок.
   * Подсказки отображены для введённых символов.
   * Максимальное число — 5.
   * Совпадения выделены.
2. Страница результатов открыта.
   * Подразделы отображены в списке.
   * Результаты отображены в блоках.
3. Значение сохранено в историю.
   * Запись отображена в «Search history».
```

**Нарушение правила — три шага и один общий результат:**

```
Шаги:
1. Открыть страницу.
2. Заполнить форму.
3. Нажать кнопку.

Ожидаемый результат:
Пользователь зарегистрирован.
```

**Исправление:**

```
Шаги:
1. Открыть страницу.
2. Заполнить форму.
3. Нажать кнопку.

Ожидаемый результат:
1. Страница регистрации открыта.
2. Поля заполнены корректными значениями.
3. Пользователь зарегистрирован.
```

## Стиль ожидаемого результата

Ожидаемый результат описывает состояние системы после выполнения конкретного шага.

Использовать формулировки прошедшего времени (пассивные конструкции):

отображено; открыто; создано; сохранено; отправлено; доступно; недоступно; возвращена ошибка; сообщение отображено; запись создана; данные обновлены; заблокировано.

Не использовать:

отображается; открывается; появляется; показывается; выводится; становится доступным; становится видимым.

| Плохо | Хорошо |
|---|---|
| Открывается страница задания. | Страница задания открыта. |
| Отображается кнопка «Сохранить». | Кнопка «Сохранить» отображена. |
| Подсказки отображаются под полем. | Подсказки отображены под полем. |

## Постусловия

При необходимости указывают итоговое состояние системы после выполнения теста.

Пример: `Созданный пользователь удалён из базы данных.`

## Группировка проверок валидации (анти-фрагментация)

Валидация одного поля (пустое значение, минимальная длина, формат, спецсимволы) = **один тест-кейс**.

Недопустимо:

- разбивать валидацию одного поля на два и более теста (пустое → TC-006, минимальная длина → TC-007);
- использовать секцию «Дополнительные шаги» — все шаги идут подряд в одном блоке «Шаги».

Правило «один шаг — одно действие» сохраняется, но все варианты валидации одного поля объединяются в один тест:

```
Шаги:
1. Оставить поле пустым.
2. Нажать кнопку «Сохранить».
3. Ввести значение длиной менее X символов.
4. Нажать кнопку «Сохранить».

Ожидаемый результат:
1. Отображено сообщение об ошибке: поле обязательно.
2. Изменения не сохранены.
3. Отображено сообщение об ошибке: минимальная длина не соблюдена.
4. Изменения не сохранены.
```

## Языковые правила

Деловой технический стиль.

Избегать: возможно; вероятно; скорее всего; при необходимости; если получится.

Формулировки должны быть однозначными и проверяемыми.
